## B. Recommended architecture

```
Phone/Laptop browser
        |
  Next.js app (UI + server code)  <- hosted on Vercel (free)
        |
  +-----+---------------------------+
  | Layers (kept in separate folders)|
  | 1. ui/            screens only   |
  | 2. services/      business rules |
  | 3. db/            DB queries     |
  | 4. agents/        prompts+schemas|
  | 5. integrations/  Meta, etc.     |
  +-----+---------------------------+
        |
  Supabase (Postgres DB + Auth + file storage + row-level security)
        |
  AI provider (Claude API) via ONE wrapper -> mock provider by default
```

Key design choices (simple English):
- **One codebase, one language (TypeScript).** Fewer moving parts for a beginner.
- **Database enforces privacy.** Supabase "Row Level Security" means even a bug in my code cannot show Client A's data to Client B.
- **Every external action goes through an Approval Gate.** Publishing, ad changes and client messages become a `pending_approval` record. Nothing is sent until a human clicks Approve. This is enforced in the service layer and cannot be skipped by an agent.
- **Mock-first integrations.** Each integration has a `mock` and a `real` version behind one interface. The UI shows a visible "MOCK / Not connected" badge so nothing is faked silently.
- **Agents are data + prompts, not magic.** Each agent = instruction file + Zod schema for output + a runner that logs cost, time, errors.
- **Job queue = a database table** (`agent_runs`) processed by a cron/route handler. No Redis or extra servers.

## C. MVP feature list (what Version 1 includes)
In the first working MVP (Phases 1-4):
1. Login (email + password), roles: Owner, Team Member, Client (view/approve only).
2. Agency dashboard: list of clients, tasks due, pending approvals.
3. Client workspace + onboarding form: brand profile, goals, tone, audience, guidelines, competitors.
4. Content module: ideas -> captions/scripts/carousel plan -> SEO metadata, generated by AI (mock first, Claude when key added).
5. Content calendar (month/week view, mobile-friendly).
6. Approval workflow: Draft -> In Review -> Changes Requested -> Approved -> Ready to Publish (manual).
7. Audit log + agent run log (who/what/when/cost).
8. Export approved content as copy-paste / CSV. Publishing stays **manual** in MVP.

Later (Phases 5+): research with source links, audit & strategy generator, Meta Ads CSV import & reports, lead tracker, proposals/packages, monthly PDF report, scheduling/publishing via official APIs, AI CEO orchestration.

**Honest flaw check on your 12 modules:** building all 12 plus 16 agents at once is how projects like this die. Most "agents" (QA, editor, scheduler, publisher) are just steps in one content pipeline. Video "production/editing" cannot be truly automated for free. In the MVP it will output **editing instructions + shot lists** for you or an editor, not rendered videos. The "AI CEO" should come last, once the single agents work.

## D. Proposed database schema (Postgres / Supabase)
Every table has `agency_id`; client-owned tables also have `client_id`. All have `created_at`, `updated_at`.

| Table | Purpose / key columns |
|---|---|
| `agencies` | name, plan |
| `profiles` | user id, agency_id, full_name, role (`owner`/`member`/`client`) |
| `clients` | agency_id, name, industry, city, status |
| `client_users` | links client-role logins to a client |
| `brand_profiles` | client_id, tone, audience, USPs, do/don't, colors, fonts, languages |
| `goals` | client_id, goal type, target, period |
| `competitors` | client_id, name, handle/url, notes |
| `research_items` | client_id, topic, summary, status |
| `sources` | research_item_id, url, title, accessed_at, verified (bool) |
| `audits` | client_id, platform, findings (json), score |
| `strategies` | client_id, pillars (json), cadence, period |
| `content_items` | client_id, type (post/reel/carousel/story), platform, title, status, scheduled_for |
| `content_versions` | content_item_id, version_no, body (json: caption/script/hooks/hashtags/SEO), created_by (user or agent) |
| `creative_briefs` | content_item_id, brief, carousel_plan, image_prompts, edit_instructions |
| `assets` | client_id, storage_path, kind, source (upload/AI) |
| `approvals` | content_item_id, requested_by, decided_by, decision, comment, decided_at |
| `comments` | content_item_id, user_id, text |
| `publish_jobs` | content_item_id, platform, status, requires_approval=true, approved_by, external_id |
| `integrations` | agency_id/client_id, provider, status (`mock`/`connected`/`error`), scopes. Tokens stored encrypted, never in frontend |
| `metrics_organic` | client_id, platform, date, reach, engagement, followers |
| `ad_campaigns` / `ad_metrics` | client_id, campaign, spend (₹), leads, CPL, date |
| `leads` | client_id, source, name, phone, status, value |
| `recommendations` | client_id, text, type, status (needs human approval to act) |
| `packages` / `proposals` | service packages, proposal lines, price in ₹, status |
| `tasks` | client_id, assignee, due, status |
| `reports` | client_id, month, file_path, status |
| `agent_definitions` | key, version, prompt_path, enabled |
| `agent_runs` | agent_key, client_id, input, output, status, error, tokens, cost_inr, duration_ms |
| `audit_logs` | user_id/agent, action, entity, entity_id, before/after, ip, at |

Security rules at DB level (RLS): staff see only their agency's rows; client logins see only their own client's approved/review items.

## G. Security and integration requirements
Security:
- Secrets only in server environment variables. `.env` is git-ignored and a `.env.example` is committed. A secret-scanning check runs before commits.
- Row Level Security on every table. A test proves Client A cannot read Client B.
- Server-side validation (Zod) on all inputs. AI output is validated too, and rejected if malformed.
- Role checks in services, not just in UI. Audit log for every create/update/approve/publish.
- Tokens for Meta etc. stored encrypted, scoped to the minimum permissions.
- Logs never contain keys, tokens or client phone numbers.
- Hard approval gate: `publish_jobs`, ad changes and client messages cannot execute without an `approved_by` human.
- Basic rate limits and a monthly AI-spend cap per agency.

Integrations (honest status):
- **Instagram/Facebook publishing:** possible only through Meta's official Graph API, needs a Meta developer app, a Business account, and often **app review**. This can take weeks. Until then: manual publishing.
- **Meta Ads reporting:** needs Marketing API access (also permission/review dependent). MVP uses **CSV import** from Ads Manager.
- **Google Ads / GA4 / Search Console:** official APIs, need OAuth set-up. Later.
- **WhatsApp client messaging:** WhatsApp Business API is paid and approval-based. MVP only drafts messages for you to copy.
- **Third-party schedulers** (e.g. Metricool) could be an alternative to building our own publishing. Decide in Phase 6.
